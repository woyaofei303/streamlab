# 面试演示、技术表达与追问

先读 [架构与链路](ARCHITECTURE.md) 和 [JD 学习指南](JD-STUDY.md)。下面保留 15 分钟演示，后半部分提供三分钟介绍、案例追问与简历表达。

先确认 `pnpm dev`、`pnpm media:fixture` 已启动。在同一浏览器、同一 origin 开两个标签页，分别使用 Alex 和 MEI；实验室先重置演示数据。不要使用真实支付资料。

## 0:00–2:00 内容发现与状态

首页展示桌面导航、分类和频道网格；搜索 River，刷新后 URL 筛选仍然保留。预约频道，在个人中心查看预约。切换手机宽度展示视频、内容、聊天的纵向布局。说明交易所项目的 React/TypeScript 经验如何迁移到这里的高频实时数据和状态一致性。

## 2:00–5:00 播放器与本地媒体链路

在 MEI 房间播放默认 HLS，切换清晰度、字幕、倍速、弹幕和剧场模式。打开「播放信息」解释示例直播状态与点播测试源的区别。

切换为 OBS 本地真实直播。通过内置 FFmpeg 推流器演示 RTMP → MediaMTX → LL-HLS；有 OBS 时换用同一个地址。停止再恢复推流，展示有限重试和手动重新加载。不要把本机视频的延迟描述为真实跨境表现。

## 5:00–7:00 IM 与房间管理

观众发送消息；主播页面置顶、禁言；观众发送失败，解除禁言后使用原消息 ID 重试。实验室启用 duplicate / reorder，解释为什么消息不会重复显示。打开 disconnect，再恢复 normal，观察断线期间消息补拉。

发起投票、提交问答。弹幕根据媒体时间调度，拖动回放后重新安排轨道；聊天虚拟列表与 Canvas 动画独立工作。

## 7:00–10:00 商业闭环

开通 MEI 月会员，在个人中心取消续费，说明当前周期不会立即失效。实验室前进 31 天显示到期；开启续费的会员显示模拟续费失败。

模拟充值 500 礼物币，送礼并再送，查看余额、累计贡献榜和消费来源。演示不足余额错误。

## 12:00–15:00 诊断与实现证据

实验室对比正常 HLS 与慢分片，展示首帧、缓冲、卡顿和事件时间线。导出会话日志，打开验证报告中的 30 次切房和消息压力测试结果。结束直播后查看真实录制回放。

收尾解释三个技术案例，避免只展示页面数量。

## 案例一：播放器生命周期

问题：切换房间时旧 HLS 实例、请求或 timer 继续运行；新页看似正常，但内存和重复请求持续增长。

实现：每次 source/retry 创建独立生命周期，所有资源在 effect cleanup 中释放；帧处理使用 ref/rAF，指标以较低频率更新页面。网络和解码错误分别恢复，manifest 失败必须重载源，不能只调用分片 startLoad。

证据：客户端路由连续切房 30 次后卸载播放器，资源计数归零；暂停和 seek 不算播放中卡顿。说明计数只是资源检查的一部分，真实长期内存分析仍需浏览器 heap/performance 工具。

## 案例二：IM 恢复与一致性

问题：断线期间丢消息、ACK 超时重试产生重复、乱序返回；主播禁言必须同步给观众。

实现：稳定消息 ID、顺序号、ACK、心跳、退避重连、按游标补拉、ID 合并和排序。失败发送重试沿用原 ID；统一 domain 规则执行权限。IndexedDB 事务提交后发送失效通知，其他标签重新查询。

证据：双标签发送/置顶/禁言测试，重复 ACK 与补拉测试，100 条/秒压力验证。明确 MSW WebSocket 是客户端模拟服务，真实服务器仍需持久日志、鉴权和背压。

## 案例三：播放质量定位

问题：起播慢不一定是 CDN 慢；也可能是清单获取、分片等待、解码、自动播放被拒或用户主动暂停。

实现：记录 load、manifest、first frame、level switch、waiting、playing、错误事件。通过同源分片故障路由隔离网络问题；真实多码率 HLS 验证画质切换，LL-HLS 使用本地媒体服务。

实验方法：同一设备、相同源、相同浏览器、相同缓存策略运行正常/慢分片各三次；比较首帧中位数和卡顿时长，不把单次波动当优化收益。区分真实采集指标、示例观众数据、第三方不可获取指标。

跨境延伸：面试讨论 DNS/TLS/首包、CDN 节点与回源、分片大小、码率梯度、缓冲策略、失败域和按地区分组的 QoE。该项目没有真实跨境 CDN，所以不捏造优化百分比。

## 三个案例怎样讲到可以追问

### A. 播放器生命周期与清单恢复

- **现象**：初始 HLS manifest 不存在时，重试一直不能起播；频繁切房还可能留下旧实例。
- **证据位置**：[Player 主 effect](../src/components/player.tsx)、[清单回归测试](../tests/e2e/regressions.spec.ts)、[30 次切房测试](../tests/e2e/media-performance.spec.ts)。
- **根因**：初始失败没有解析到 level，startLoad 无法替代重新获取清单；切源还必须释放旧 HLS/video 关联资源。
- **处理**：网络与媒体 fatal 分类，初始清单重新 loadSource，后续网络错误 startLoad，解码错误 recoverMediaError；应用层恢复两次，结束后手动重试。统一 cleanup 清 timer/监听/帧回调、destroy HLS、清 src。
- **结果**：历史回归中 404 到达可重试 UI，30 次客户端切房后实例计数为 0。不能把计数器归零说成完整 heap 泄漏证明。
- **进一步追问**：如何区分应用重试与库内部请求重试？切换源时 Promise 迟到怎么办？原生 HLS 与 iframe 能否复用同样的指标？

### B. 消息恢复不能被缓存刷新绕过

- **现象**：模拟 WS 断线后，Query 刷新仍可能把新消息带进列表，导致“补拉成功”测试证明了错误的东西。
- **证据位置**：[Chat 的 receive/connect](../src/components/chat.tsx)、[MSW 的 sync](../src/mocks/browser.ts)、[双标签测试](../tests/e2e/flows.spec.ts)。
- **根因**：业务快照和消息通道都能把新消息写入同一列表，断线状态不再对应真实消息可达性。
- **处理**：新消息只经过 WS/补拉；Query 只修补已接收消息的管理状态。发送复用稳定 ID，ACK/重复批次经 Map 合并；重连带 after。
- **结果**：测试先断言离线期间消息不可见，再恢复 normal 确认补拉。已有压力记录包含 6000 条发送、4000 条保留、27 行 DOM；这些数字有明确设备和场景。
- **进一步追问**：after 是最大已见还是最大连续序号？旧消息被淘汰后如何恢复？当前没有处理这些生产协议细节，应直接说明。

### C. 用可复现实验定位播放质量

- **现象**：起播等待和播放中卡顿经常被混算，难以判断调参是否有效。
- **证据位置**：[指标口径](ARCHITECTURE.md)、[媒体故障路由](../src/app/api/media/fault/[...path]/route.ts)、[实验脚本](../scripts/measure-playback.mjs)、[原始数据](evidence.json)。
- **处理**：首帧后非暂停/seek 的 waiting 才计重缓冲；对同一素材做正常、额外等待和传输限速对照，记录首帧、level_switch 与 stall。
- **历史观察**：正常三轮首帧中位数 72ms，慢分片 1567ms；限速一轮 720p → 360p、6 次卡顿。数据来自本机开发环境，不是线上 SLA。
- **结论**：能用实验区分等待、吞吐不足和状态误计；不能把“移除人为延迟”的差值包装成生产优化成果。
- **进一步追问**：用户感知起播的起点是什么？ABR 降档仍卡顿怎么办？若有地区差异，如何分组并结合 CDN 数据验证？

## 高频追问与回答要点

### 1. 为什么不用一个全局 store 存播放器？

HLS/Peer/MediaStream 是带生命周期的可变资源，放 ref 并在 effect 中创建/释放更直接；播放状态和少量汇总指标才进入 React state。全局 store 不会自动清理资源，也不能解决闭包和异步返回竞态。需要跨页小窗播放时才重新设计播放器的所有权。

### 2. 为什么有 Query 还需要 Context 和 IndexedDB？

Query 缓存请求结果、处理失效；Context 传递当前用户/语言/动作等；IndexedDB 提供跨刷新存储和本地事务。当前 Query 查整份 state 是演示简化，大规模场景要按业务键拆查询，不能依靠框架名称证明性能。

### 3. 这算 Next.js SSR 项目吗？

使用 App Router 和服务端工具路由，但业务内容等浏览器 MSW 初始化后才加载。不能把它说成已实现完整内容 SSR/SEO。公开频道目录可在后续采用服务端获取，而设备和播放器仍需要客户端边界。

### 4. hls.js 是用 JavaScript 解码 H.264 吗？

本项目由 hls.js 处理 HLS 清单、分片加载、转封装和选档，通过 MSE 接到 video；实际媒体解码渲染由浏览器媒体实现完成。FFmpeg 在生成素材时做编码/转码，这与浏览器播放阶段不同。

### 5. 自动播放被拒时增加重试有用吗？

权限/浏览器播放策略与网络故障不同。捕获 play() Promise 拒绝，显示明确的用户播放入口；不能把所有失败当成网络重试。本地播放器默认静音也不意味着所有平台都保证自动播放成功。

### 6. 怎么定义首帧和卡顿率？

先对齐起止点：本项目是播放器初始化到视频帧回调，不包含所有页面和业务鉴权阶段。当前有卡顿次数与时长，缺少完整有效播放分母；要区分“发生卡顿的会话比例”与“重缓冲时间占比”，并排除主动暂停等区间。

### 7. hls.js 开启 lowLatencyMode 后就低延迟了吗？

还需要支持 LL-HLS 的源、合理的编码/分片和播放器追赶策略。它不是把普通 HLS 点播变实时直播的开关；降低目标延迟也可能减少抗抖动余量。本项目没有测得端到端延迟，不能报一个保证值。

### 8. 虚拟列表是不是解决了所有 IM 性能问题？

它只减少 DOM。消息数组、去重集合、待发消息、通知和弹幕也要有容量策略。当前消息窗口有界，但 pending 失败项和其他业务记录没有完整长期淘汰方案；本地 100 条/秒实验不等于百万在线能力。

### 9. WebSocket 为什么还要 ACK？

send 不代表业务校验成功或持久化完成。ACK 让客户端确认消息被业务接受；断开前后的未知结果通过稳定 ID 重试去重。连接顺序、业务顺序与持久化顺序是相关但不同的问题。

### 10. 消息 exactly-once 怎么做？

先避免承诺网络层“绝对恰好一次”。当前采用允许重复的重试/补拉，加业务 ID 去重，让窗口内同一条只展示一次。生产还要持久幂等记录、序号缺口恢复和可恢复游标；本项目有界存储不支持无限历史保证。

### 11. 取消续费和退款有什么区别？

取消续费不撤销已经支付的周期，until 保留；退款成功则撤销对应订单权益。当前会员周期固定 30 天，续费失败来自模拟时钟。真正的支付结果和权益必须由服务端判定。

### 12. 为什么支付超时不能直接再下新订单？

服务可能已经提交但响应丢失，新 key 会被视为新意图。应该用原幂等键查询/重试，并明确处理中状态。当前弹窗在同一次意图内复用 key，但刷新后的意图恢复、同键不同载荷校验还未完整实现。

### 13. 并发送礼如何避免超支？

读余额、校验、扣减、写交易、追加礼物消息在同一 IDB readwrite 事务中完成；不能先读出余额再异步写回。这里是同 origin 本机原子性，迁到后端需要真正的服务端并发控制、账务规则和幂等约束。

### 14. WebRTC 同机成功，为何公网失败？

信令交换成功不等于媒体路径可达。需检查 ICE 候选、连接状态、NAT/防火墙和编解码协商；本项目没有 STUN/TURN。MediaMTX 8889 处理 HTTP SDP，8189 UDP/TCP 承载配置中的媒体连接路径，不是同一个端口职责。

### 15. getUserMedia 返回之前用户已经离开怎么办？

用请求代次或取消身份标记结果是否仍有效。设备授权 Promise 未必能直接中止，迟到的 stream 仍要主动 stop 全部轨道。只清 React state 不会释放摄像头；静音也不是释放。

### 16. 已经接收视频轨道，为什么仍要单独验收音频？

轨道协商、编码、播放策略和实际声音输出各有条件。项目测试确认音频轨道为 live，不代表所有真实设备和浏览器都已试听；OBS 的 AAC 路径也不能未经验证就认为 WebRTC 音频兼容。

### 17. CDN / 跨境卡顿，你会先改什么？

先按地区、运营商、播放器/设备版本分组，观察 DNS/连接、首包、分片吞吐、缓存命中、回源和解码长任务，再确定是网络、分发还是终端问题。一次只验证一个假设，保留相同源、缓存策略和设备条件。当前项目只有故障注入，不能声称已经做过真实跨境优化。

### 18. 你做过播放器内核改造吗？

这个项目做的是播放器集成、生命周期与 QoE，不是 hls.js 内核 fork。能解释当前清单/分片/缓冲/ABR 的分工；若进一步研究内核，会先复现问题、定位对应 controller/loader、补回归再考虑修改，不能把配置参数调整说成内核改造。

### 19. 如何和后端、产品、测试配合？

先约定业务场次与媒体信号的状态区别、权益生效/撤销时间、消息 ID/ACK/恢复协议、错误码和指标口径。将正常/失败/超时/重复操作写进验收步骤，前端按契约做模拟，联调时替换数据来源而不是临时拼状态。项目中的 API、实验记录和 E2E 就是这一协作方式的产物。

### 20. 如果只剩一周，优先补什么？

你已有 React/TS 基础，先把 HLS 请求链路、播放器清理、IM 补拉、支付未知结果四个主题练到可白板和可演示；再练一次 WebRTC 协商与弱网分析。FLV、Flutter/原生、真正 CDN 优化列为明确的后续补强，不为覆盖名词牺牲核心理解。
